## Not confirmed from source

The verifier could not settle these either way:

- config.json location: whether Electron's runtime userData folder name on each OS matches native's first candidate ('Buddy', then 'hs-buddy', '@hemsoft/buddy') was not confirmed by running either app; only the candidate list and electron-builder productName were read.
- window-state.json: cross-app restore (Electron reading the nativeGeometry/nativeDisplayUuid fields native writes) was checked only on the native side and in the head of electron/windowsWindowState.ts, not end to end.
- Review-complete sound: both apps poll only from the PR detail view (Electron hooks mount in PullRequestDetailPanel; native polls only the currently selected PR). Whether Electron keeps polling for a PR tab that is open but in the background, which native would not, was not traced through the tab mounting code.
- GitHub Copilot SDK runtime: Electron falls back to a `copilot` binary on PATH when the bundled CLI is absent (copilotClient.ts:76); whether native has any fallback beyond the SDK-bundled runtime (copilot_runtime.rs) was not confirmed.
- Dashboard auto-refresh: native keeps intervals in native.autoRefresh; where (or whether) it tracks last-refreshed time was not located, so only 'no persisted counterpart found' is asserted.
- Convex jobs/schedules/runs: Electron also uses schedules.toggle, schedules.get and jobs.get; native has no such strings and presumably derives these from schedules:update and the list queries, but the equivalent native UI paths were not opened (owned by the automation area).
- copilotResults: Electron's active-result badge uses copilotResults.countActive; native has no such call and may derive the count from copilotNative:listResultsByStatus, which was not traced.
- Evidence entries are tests and scripts whose names were confirmed present in the checkout; none were executed (read-only task), so they show coverage exists, not that it passes.
