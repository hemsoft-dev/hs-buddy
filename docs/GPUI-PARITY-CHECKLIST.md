# GPUI parity checklist

This checklist compares the Electron app with its native Rust/GPUI replacement,
capability by capability. It is the source-linked checklist that
[#823](https://github.com/hemsoft-dev/hs-buddy/issues/823) requires before the
native app can become the primary desktop app.

It reflects `main` at commit
[`55e4ee06`](https://github.com/hemsoft-dev/hs-buddy/commit/55e4ee0653124c0aa52d3d354d2eba246356bb41)
(2026-11-21). Every source link is a permalink to that commit, so the links keep
working as the code moves, and a row is out of date as soon as its code changes.
A row ported later links the commit that ported it instead, starting with
Escape in the Tempo worklog editor
([#984](https://github.com/hemsoft-dev/hs-buddy/pull/984), commit `0f9af531`).
The remaining work is tracked per area in #988 to #995.

## How to read a row

- **Capability**: one user-visible thing the Electron app does: a route, a
  sidebar or assistant flow, an action, a menu item, a keyboard shortcut, a
  persisted setting or data store, a migration, or an external integration.
- **Electron**: *Implemented* means real behavior. *Placeholder* means the
  route or control exists but does nothing yet. *Label only* means a label or
  enum entry with no behavior behind it.
- **Native state**:
  - *Ported*: the native app has equivalent behavior.
  - *Partly ported*: it has the capability with a named difference.
  - *Missing*: no native counterpart was found.
  - *Placeholder*: the native app shows a placeholder.
  - *Not applicable*: Electron-only by nature, such as Chromium DevTools.
- **Native evidence**: tests or installed scenes found in the source that
  exercise the native behavior. "None found" means no test was found, not that
  the behavior is broken.

## How this was made, and its limits

The rows come from reading source, not from running either app. For each of the
eight areas, one pass enumerated the Electron routes, components, IPC handlers,
menu items, shortcut registrations and store keys and looked for the native
counterpart of each. A second, independent pass then opened every cited line,
corrected the state where the code did not support it, and searched for
capabilities the first pass had missed. The second pass made 209
corrections. A script then confirmed that every cited path exists and that
every cited line number is inside its file. Review of the pull request that
added these pages corrected two more rows.

What that does and does not establish:

- A state is a judgment from source. Nothing was built, launched or tested to
  produce this list.
- An evidence entry means a test or scene exists that covers the behavior. It
  was not executed for this checklist.
- 58 points could not be settled from this repository, mostly because the
  deciding code is in an external crate or package. Each area page ends with
  its own list.
- Granularity is uneven by design: one row per route or meaningful action
  group, not one per button.
- *Ported* is the least checked state. Review of the pull request that added
  these pages sampled the rows and found two marked *Ported* that differ in
  behavior: the embedded browser's address check and the Today task list. Both
  are corrected, but the remaining *Ported* rows have not been re-checked
  since. Treat a *Ported* row as "no difference found", not as "proven equal".

## Keeping it current

When a change ports, alters or removes a capability, update its row in the same
pull request: the state, the native source link (as a permalink to a commit that
contains the code), the difference and the evidence. When a new Electron
capability lands, add a row. Regenerating the whole list is only worth it if
the two apps have drifted far from these pages.
